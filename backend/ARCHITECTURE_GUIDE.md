# Backend Application Guide

Этот файл фиксирует выводы по проекту по порядку разбора. Идея: читая его сверху вниз, можно понять, из каких базовых частей собирается нормальное backend-приложение и зачем каждая часть нужна.

## 1. Точка входа приложения

В Go исполняемое приложение начинается с пакета:

```go
package main
```

и функции:

```go
func main()
```

Что нужно делать:

Создавать отдельную точку входа приложения, обычно в директории `cmd`.

Зачем:

`cmd/main.go` не должен содержать всю бизнес-логику. Его задача - собрать приложение: прочитать конфиг, подключить инфраструктуру, создать сервисы, зарегистрировать роуты и запустить сервер.

Что запомнить:

`main.go` - это сборщик приложения, а не место для бизнес-логики.

## 2. Импорты

Импорты показывают, из каких частей собирается приложение.

Обычно они делятся на группы:

- стандартная библиотека Go;
- внешние зависимости;
- внутренние пакеты проекта.

В этом проекте стандартная библиотека используется для HTTP, логов, ошибок, сигналов остановки, времени и контекстов.

Внешние зависимости:

- `golang-migrate/migrate` - миграции базы данных;
- `gorilla/mux` - HTTP-роутер.

Внутренние пакеты:

- `config` - чтение настроек;
- `pg` - подключение к PostgreSQL;
- `pgrepo` - работа с базой данных;
- `services` - бизнес-логика;
- `httpserver` - HTTP-обработчики.

Что нужно делать:

Разделять код по ответственности. Не складывать конфиг, SQL, бизнес-логику и HTTP-обработчики в один файл.

Зачем:

Так приложение проще читать, тестировать и менять. Каждый слой отвечает за свою часть.

Что запомнить:

По импортам в `main.go` часто можно быстро понять архитектуру приложения.

## 3. Импорт через нижнее подчеркивание

Пример:

```go
_ "github.com/golang-migrate/migrate/v4/database/postgres"
_ "github.com/golang-migrate/migrate/v4/source/file"
```

Что это значит:

Пакет импортируется не для прямого вызова функций, а ради побочного эффекта.

В этом проекте такие импорты регистрируют драйвер PostgreSQL и источник миграций из файлов.

Что нужно делать:

Использовать `_`-импорт только когда библиотека явно требует регистрацию драйвера или плагина через импорт.

Зачем:

Без таких импортов `migrate` может не знать, как работать с PostgreSQL или как читать миграции из файловой системы.

Что запомнить:

`_` перед импортом означает: "подключи пакет, но напрямую я его не использую".

## 4. Разница между `fmt` и `log`

`fmt` нужен для форматирования текста, строк и ошибок.

Пример:

```go
return fmt.Errorf("pg.Dial failed: %w", err)
```

Здесь `fmt` не пишет в консоль. Он создает новую ошибку с дополнительным контекстом.

`log` нужен для логирования событий приложения.

Пример:

```go
log.Fatal(err)
```

`log.Fatal` печатает ошибку и завершает процесс с кодом `1`.

Что нужно делать:

Использовать `fmt.Errorf` для оборачивания ошибок, а `log` - для вывода событий и ошибок приложения наружу.

Зачем:

Ошибки должны подниматься по стеку с контекстом, а логирование должно происходить на границах приложения.

Что запомнить:

`fmt` чаще формирует текст, `log` сообщает о событии приложения.

## 5. Функция `main`

Типичный паттерн:

```go
func main() {
	if err := run(); err != nil {
		log.Fatal(err)
	}
}
```

Что происходит:

`main()` вызывает `run()`. Если `run()` возвращает ошибку, приложение логирует ее и завершается.

Зачем выносить код в `run()`:

`main()` не может вернуть ошибку, а `run()` может. Поэтому основную логику запуска удобно держать в `run() error`.

Что важно про `log.Fatal`:

`log.Fatal` вызывает `os.Exit(1)`. После `os.Exit` отложенные вызовы `defer` не выполняются.

Поэтому cleanup лучше делать внутри `run()`, где `defer` успеет выполниться до возврата ошибки в `main()`.

Что запомнить:

`main()` должен быть тонкой оберткой. Основная логика запуска должна быть в функции, которая возвращает ошибку.

## 6. TTL токена

Пример:

```go
const tokenTTL = time.Minute * 5
```

TTL означает `Time To Live`, то есть время жизни.

В этом проекте токен живет 5 минут.

Что нужно делать:

Выносить важные настройки поведения в именованные константы или конфиг.

Зачем:

Так код проще читать. Название `tokenTTL` сразу объясняет смысл значения.

Что запомнить:

Не оставлять в коде непонятные "магические числа", особенно если они управляют поведением приложения.

## 7. Чтение конфига

Пример:

```go
cfg := config.Read()
```

Что происходит:

Приложение получает настройки из внешнего мира.

В этом проекте конфиг содержит как минимум:

- `DSN` - строку подключения к PostgreSQL;
- `MigrationsPath` - путь к миграциям;
- `HTTPAddr` - адрес HTTP-сервера.

Что нужно делать:

Не хардкодить настройки в коде. Читать их из конфигурации: environment variables, файлов, флагов или других источников.

Зачем:

Один и тот же код должен работать в разных окружениях:

- local;
- Docker;
- staging;
- production.

Меняться должен конфиг, а не код.

Что запомнить:

Конфиг - это граница между окружением и приложением. Обычно это один из первых шагов запуска.

## 8. Базовая цепочка backend-приложения

Нормальное backend-приложение обычно собирается в таком порядке:

```text
config
  -> infrastructure connections
  -> migrations
  -> repositories
  -> services
  -> handlers
  -> routes
  -> server lifecycle
```

Что означает каждый шаг:

`config` - получить настройки.

`infrastructure connections` - подключиться к базе, Redis, очередям или внешним API.

`migrations` - привести схему базы данных к нужному состоянию.

`repositories` - изолировать работу с хранилищем данных.

`services` - держать бизнес-логику.

`handlers` - принимать HTTP-запросы и вызывать сервисы.

`routes` - связать URL и HTTP-методы с обработчиками.

`server lifecycle` - запустить сервер и корректно остановить его.

Что запомнить:

Это не случайный набор папок. Это последовательность зависимостей: каждый следующий слой опирается на предыдущие.

## 9. Подключение к базе данных

Пример:

```go
pgDB, err := pg.Dial(cfg.DSN)
if err != nil {
	return fmt.Errorf("pg.Dial failed: %w", err)
}
```

Что происходит:

Приложение пытается подключиться к PostgreSQL, используя DSN из конфига.

`pgDB` - объект подключения к базе данных. Дальше он будет передан в репозитории.

`err` - ошибка подключения, если база недоступна, DSN неправильный или есть проблема с сетью.

Что нужно делать:

Подключать внешнюю инфраструктуру в начале запуска приложения и сразу проверять ошибку.

Зачем:

Если приложение не может подключиться к базе, нет смысла запускать HTTP-сервер. Лучше упасть на старте с понятной ошибкой, чем принимать запросы и ломаться позже.

Почему используется `fmt.Errorf`:

```go
return fmt.Errorf("pg.Dial failed: %w", err)
```

Так исходная ошибка не теряется, а получает контекст: теперь понятно, что сбой произошел именно на этапе `pg.Dial`.

`%w` означает wrapping error. Обернутую ошибку потом можно проверить через `errors.Is` или `errors.As`.

Что запомнить:

Внешние зависимости приложения нужно инициализировать явно, проверять ошибки сразу и возвращать ошибки наверх с контекстом.

## 10. Запуск миграций базы данных

Пример:

```go
if pgDB != nil {
	log.Println("Running PostgreSQL migrations")
	if err := runPgMigrations(cfg.DSN, cfg.MigrationsPath); err != nil {
		return fmt.Errorf("runPgMigrations failed: %w", err)
	}
}
```

Что происходит:

Если объект базы создан, приложение запускает PostgreSQL-миграции.

Миграции - это версионированные изменения схемы базы данных:

- создать таблицу;
- добавить колонку;
- создать индекс;
- добавить constraint;
- изменить структуру таблиц.

Что нужно делать:

Хранить изменения схемы базы в миграциях, а не менять базу руками.

Зачем:

Приложение и база должны развиваться синхронно. Если код ожидает таблицу `books`, эта таблица должна быть создана предсказуемым способом.

Миграции позволяют:

- поднять базу с нуля;
- обновить базу на staging или production;
- повторить одинаковую схему у всех разработчиков;
- понимать историю изменений базы.

Почему миграции запускаются после подключения к базе:

Чтобы применить миграции, приложению нужен доступ к PostgreSQL. Поэтому сначала `pg.Dial`, потом `runPgMigrations`.

Что запомнить:

Если приложение зависит от структуры базы, эту структуру нужно описывать кодом миграций и применять при запуске или в отдельном deploy-шаге.

## 11. Создание репозиториев

Пример:

```go
userRepo := pgrepo.NewUserRepo(pgDB)
bookRepo := pgrepo.NewBookRepo(pgDB)
categoryRepo := pgrepo.NewCategoryRepo(pgDB)
cartRepo := pgrepo.NewCartRepo(pgDB)
```

Что происходит:

Приложение создает объекты для работы с PostgreSQL.

Каждый репозиторий отвечает за свою часть данных:

- `UserRepo` - пользователи;
- `BookRepo` - книги;
- `CategoryRepo` - категории;
- `CartRepo` - корзина.

Все они получают `pgDB`, потому что им нужен доступ к базе данных.

Что нужно делать:

Выносить работу с базой данных в отдельный слой репозиториев.

Зачем:

Чтобы SQL и детали хранения не расползались по HTTP-обработчикам и бизнес-логике.

Хорошая граница выглядит так:

```text
service -> repository -> database
```

Сервис говорит: "создай пользователя" или "получи книгу".

Репозиторий знает, какой SQL-запрос для этого выполнить.

Что запомнить:

Репозиторий - это слой доступа к данным. Он прячет детали базы от остального приложения.

## 12. Создание сервисов

Пример:

```go
tokenService := services.NewTokenService(tokenTTL)
userService := services.NewUserService(userRepo)
bookService := services.NewBookService(bookRepo)
categoryService := services.NewCategoryService(categoryRepo)
cartService := services.NewCartService(cartRepo)
```

Что происходит:

Приложение создает слой сервисов.

Сервисы используют репозитории и реализуют бизнес-логику приложения.

В этом проекте:

- `TokenService` - работа с токенами;
- `UserService` - логика пользователей;
- `BookService` - логика книг;
- `CategoryService` - логика категорий;
- `CartService` - логика корзины.

Что нужно делать:

Держать бизнес-правила в сервисах, а не в HTTP-обработчиках и не в репозиториях.

Зачем:

HTTP-обработчик должен заниматься HTTP: прочитать запрос, вызвать сервис, вернуть ответ.

Репозиторий должен заниматься базой: выполнить запрос, сохранить или получить данные.

Сервис должен заниматься смыслом операции: проверить правила, скоординировать несколько репозиториев, принять бизнес-решение.

Что запомнить:

Сервис - это слой бизнес-логики. Он находится между transport-слоем и repository-слоем.

## 13. Создание HTTP server / transport-слоя

Пример:

```go
httpServer := httpserver.NewHttpServer(
	userService,
	tokenService,
	bookService,
	categoryService,
	cartService,
)
```

Что происходит:

Приложение создает объект HTTP-слоя. Внутрь передаются сервисы, которые нужны обработчикам запросов.

В пакете `httpserver` есть структура:

```go
type HttpServer struct {
	userService     UserService
	tokenService    TokenService
	bookService     BookService
	categoryService CategoryService
	cartService     CartService
}
```

Она хранит зависимости, через которые HTTP handlers вызывают бизнес-логику.

Что нужно делать:

Держать HTTP-логику отдельно от сервисов и репозиториев.

HTTP handler должен:

- прочитать данные из запроса;
- вызвать нужный сервис;
- обработать ошибку;
- вернуть HTTP-ответ.

HTTP handler не должен напрямую писать SQL или содержать сложные бизнес-правила.

Зачем:

Так transport-слой можно заменить или расширить. Например, кроме HTTP можно добавить gRPC или background jobs, а сервисы останутся теми же.

Что важно про интерфейсы:

`httpserver` зависит не от конкретных структур сервисов, а от интерфейсов:

```go
type UserService interface { ... }
type BookService interface { ... }
```

Это упрощает тестирование HTTP-обработчиков: вместо настоящих сервисов можно подставить mock.

Что запомнить:

`HttpServer` - это не сам сетевой сервер. Это объект transport-слоя, который хранит handlers и middleware, а реальный `http.Server` создается позже.

## 14. Создание router и базового route

Пример:

```go
router := mux.NewRouter()
router.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
	_, _ = w.Write([]byte("Book shop API v0.1"))
}).Methods("GET")
```

Что происходит:

Создается HTTP-router, который будет связывать URL и HTTP-методы с обработчиками.

`mux.NewRouter()` создает router из библиотеки `gorilla/mux`.

`HandleFunc("/", ...)` регистрирует handler для пути `/`.

`.Methods("GET")` ограничивает этот handler только GET-запросами.

Что такое handler:

```go
func(w http.ResponseWriter, r *http.Request)
```

`r *http.Request` - входящий HTTP-запрос: метод, URL, headers, body.

`w http.ResponseWriter` - объект, через который handler пишет HTTP-ответ клиенту.

Что делает `w.Write`:

```go
w.Write([]byte("Book shop API v0.1"))
```

Записывает тело HTTP-ответа.

Строка переводится в `[]byte`, потому что `Write` принимает байты.

Что означает:

```go
_, _ = w.Write(...)
```

`Write` возвращает два значения:

- количество записанных байт;
- ошибку записи.

В этом месте оба значения намеренно игнорируются.

Что нужно делать:

Регистрировать routes отдельно от бизнес-логики. Router должен только связывать путь и метод с нужным handler.

Зачем:

Так по `main.go` быстро видно внешний API приложения: какие endpoint есть и какие handlers их обслуживают.

Что запомнить:

Router - это таблица маршрутов приложения. `ResponseWriter` - способ отправить ответ клиенту.

## 15. Authentication и authorization

Термины:

`Authentication` - проверка личности пользователя. Вопрос: "кто ты?"

Пример: пользователь прислал username/password, приложение проверило пароль и выдало token.

`Authorization` - проверка прав пользователя. Вопрос: "что тебе можно?"

Пример: пользователь уже известен по token, но для создания книги нужно быть admin.

В этом проекте:

- `POST /signup` - регистрация пользователя;
- `POST /signin` - вход пользователя и получение JWT token;
- `CheckAuthorizedUser` - проверка, что пользователь вошел;
- `CheckAdmin` - проверка, что пользователь вошел и является admin.

### SignUp flow

Цепочка:

```text
HTTP POST /signup
  -> httpServer.SignUp
  -> decode JSON в AuthRequest
  -> validate username/password
  -> bcrypt hash password
  -> domain.User
  -> userService.CreateUser
  -> userRepo.CreateUser
  -> INSERT INTO users
  -> HTTP 200 {"ok": true}
```

Что важно:

Пароль не сохраняется как обычный текст. Перед сохранением он превращается в bcrypt hash.

### SignIn flow

Цепочка:

```text
HTTP POST /signin
  -> httpServer.SignIn
  -> decode JSON в AuthRequest
  -> validate username/password
  -> userService.GetUser
  -> userRepo.GetUser
  -> SELECT user by username
  -> bcrypt compare password with hash
  -> tokenService.GenerateToken
  -> HTTP 200 {"token": "..."}
```

Что важно:

При входе приложение не расшифровывает пароль из базы. Оно сравнивает обычный пароль из запроса с bcrypt-хешем из базы.

### JWT token

`TokenService` создает JWT с claims:

- `user_id`;
- `user_name`;
- `admin`;
- `issued_at`;
- `expires_at`.

Потом этот token клиент должен отправлять в header:

```text
Authorization: Bearer <token>
```

### Middleware flow

Для защищенных routes используется middleware:

```go
httpServer.CheckAuthorizedUser(...)
httpServer.CheckAdmin(...)
```

Цепочка:

```text
HTTP request
  -> read Authorization header
  -> remove "Bearer " prefix
  -> tokenService.GetUser(token)
  -> parse and validate JWT
  -> convert claims to domain.User
  -> put user into request context
  -> call next handler
```

Что запомнить:

Authentication в этом проекте происходит через username/password и выдачу JWT. Authorization происходит позже через проверку JWT и поля `admin`.

Практические замечания:

- JWT secret сейчас захардкожен в коде, в нормальном проекте его нужно читать из конфига.
- `TokenService` принимает `ttl`, но внутри `GenerateToken` сейчас использует `time.Minute * 15`, а не `s.ttl`.
- Ошибки invalid token сейчас отдаются как internal error, обычно для этого используют HTTP 401.
